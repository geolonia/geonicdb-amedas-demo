# 札幌積雪タイムラプス: NGSI-LD ブローカーによるリアルタイム配信デモ 設計書

- 作成日: 2026-10-04
- 関連: [Issue #2](https://github.com/geolonia/geonicdb-amedas-demo/issues/2)、親 [Issue #1](https://github.com/geolonia/geonicdb-amedas-demo/issues/1)
- 状態: ドラフト(レビュー前)

## 1. 目的と前提

### 1.1 目的

FOSS4G Hokkaido 2026(2026-11-28、トナリエ北広島、持ち時間 15〜20分(質疑を含む))での発表で使うデモを作る。NGSI-LD ブローカーのリアルタイム配信で何ができるかを、札幌市10区の2025年11月の観測データを使った積雪タイムラプスで見せる。

### 1.2 成功の基準

1. 会場のノート PC 1台で、取りこぼしなく動作する(ブローカー、Mosquitto、リプレイ、地図がすべてローカル)。
2. 第三者が、OSS のブローカー(Stellio)で再現できる形で GitHub に公開されている。
3. 「録画の再生ではなく、いま配信されている」ことが、画面から伝わる。

### 1.3 決定済みの前提

| 項目 | 内容 |
|---|---|
| 主題 | ブローカーという一般的な仕組み(OSS でも実現できる)で、どのようなリアルタイム配信ができるかを示す。「天気アプリの代わり」ではなく「ブローカーによるリアルタイム配信のショーケース」と位置づける |
| データ | 札幌市10区の観測データ(2025年11月、10分値、CC BY 4.0)。北広島市には公開された観測データがないため、対象は札幌市に統一し、画面と発表で札幌市と明示する |
| 配信経路 | リプレイ用プログラムが観測値をブローカーへ順次書き込む。ブローカーの購読通知(NGSI-LD Subscription、MQTT)が、Mosquitto の WebSocket を通って地図アプリに届く |
| 公開 | コードは GitHub で公開する。公開リポジトリの手順は、OSS のブローカー(Stellio + Mosquitto の docker-compose)で動く形にする。GeonicDB 固有の起動手順は非公開側に置く |
| 対象外 | 除雪出動のシミュレーション、ひまわり衛星画像。定点カメラは当日の補助的な見せ方にとどめ、この設計書の範囲外とする |

### 1.4 リポジトリの扱い

`geolonia/geonicdb-amedas-demo` は、すでに PUBLIC である。このリポジトリを使い続け、README と説明文を札幌積雪デモ向けに書き換える(2026-10-04 に確定)。リポジトリ名に GeonicDB が残るが、発表では「このデモを動かしているブローカーの一つ」として扱う。

### 1.5 不変条件

- ブローカーへの書き込みは、**区の間も含めて逐次**に行い、並列にしない(GeonicDB の standalone 実行は、テナントごとの通知の同時実行上限が5で、並列に書くと HTTP/MQTT の通知が黙って欠落する)。
- 再生用のテナントは、ライブ用と分ける(同じエンティティへの再書き込みは、どのブローカーでも時系列履歴を汚す)。
- 公開リポジトリには、GeonicDB のソース、サブモジュール、SDK、内部ドキュメントの内容、調査レポート、`.env`、AWS の認証情報を含めない。
- 区の境界データは、国土数値情報の元データから作り直す(試作で使った配布元はライセンス表記がない)。

## 2. 全体構成

### 2.1 データの流れ

```
札幌市 CKAN (CSV)
   │ ① prepare(ビルド時に1回)
   ▼
data/*.json  (観測値 + 観測地点)
   │ ② setup: エンティティ作成と購読登録
   ▼
NGSI-LD ブローカー ◄── ③ replay(時計に合わせて逐次 PATCH)
   │ 通知(MQTT)
   ▼
Mosquitto ── WebSocket ──► ④ web(MapLibre + mqtt.js)
```

### 2.2 方式

Node.js の小さなスクリプト群と、Vite 製(素の JavaScript)の静的な地図アプリを、1つのリポジトリに置く。ブローカーは標準の NGSI-LD API だけで操作し、ブローカー間の違いは環境変数と引数で吸収する。アダプター層、型付きの SDK は作らない(発表までの期間に対して過剰であり、OSS での再現性にも寄与しないため)。

### 2.3 リポジトリ構成

| パス | 役割 |
|---|---|
| `scripts/prepare/` | CSV → NGSI-LD 向け JSON への変換。出典と加工内容を明記する |
| `scripts/replayer/` | `setup`(エンティティ作成と購読登録)と `replay`(逐次書き込み) |
| `web/` | 地図アプリ |
| `compose/` | Stellio と Mosquitto の docker-compose(主経路) |
| `data/` | 変換後の観測値、観測地点、区の境界、出典(`ATTRIBUTION.md`) |
| `docs/` | 設計書、実装計画 |

## 3. データ変換と観測地点

### 3.1 入力

札幌市 CKAN のデータセット `sapporo_weather` から、2025年の10区分の CSV を取得する(CC BY 4.0)。対象は **2025-11-01〜11-30 のみ**。CSV は UTF-8(BOM 付き)で、列は `日付, 時刻, 気温(℃), 風向(度), 風速(m/s), 降水量(mm), 積雪深(cm), 前１時間降雪量(cm)`。

### 3.2 変換(`scripts/prepare/`)

- 取得した CSV は `data/raw/` にキャッシュする(gitignore)。
- 変換は純関数にする。CSV の文字列を入力に受けて、観測値の配列を返す。
- 取り扱いのルール:
  - BOM を除去する。
  - `24:00` は、翌日の `00:00` として扱う。
  - 時刻は JST で解釈し、`observedAt` は UTC の ISO 8601 で出力する。
  - `-` や空欄は欠測として扱い、その属性を省略する(0 に変換しない)。気温は11/1〜10付近に欠測が多いため、属性ごとに独立して扱う。
  - 前1時間降雪量は、毎正時の行にだけ値を持たせる(保持して書き込み続ける形にはしない)。

### 3.3 出力(コミットする)

| ファイル | 内容 |
|---|---|
| `data/observations/<ward>.json` | 区ごとの観測値 |
| `data/stations.json` | 観測地点のメタ情報(区コード、名称、座標、出典、備考) |
| `data/wards.geojson` | 区の境界(3.5) |
| `data/ATTRIBUTION.md` | 札幌市(CC BY 4.0)、国土数値情報(国土交通省)、気象庁の出典と、加工内容 |

変換後のデータ(約1MB)をコミットする目的は、再現時の手間を減らすことにある。

### 3.4 NGSI-LD のモデル

- エンティティの型は `WeatherObserved`、ID は `urn:ngsi-ld:WeatherObserved:sapporo-<ward>`。
- 属性は `temperature`、`snowHeight`、`precipitation`、`windSpeed`、`snowfall1h`。それぞれに `unitCode` と `observedAt` を付ける。
- 位置は、観測点(土木センター)の座標を `GeoProperty` として持たせる。
- 区の面の描画は地図側の責務とし、NGSI-LD 側には持たせない。

### 3.5 観測地点の座標と区の境界

- 観測地点の座標は、各区の土木センターの所在地から作る(国土地理院の住所検索などを使う)。
- **北区は観測点が2か所ある**。データがどちらのものかを、実装の最初に確認する。確定できなければ、確認結果と判断をこの設計書に追記する。
- 区の境界は、国土数値情報の行政区域(N03)の元データから、札幌市10区を抽出して作る。出典を画面とドキュメントに表記する。

### 3.6 検証

- `node:test` で、BOM、`24:00`、欠測、JST→UTC、正時の判定を単体テストする。
- 件数チェック: 1区あたり 30日×144点=4,320点のうち、11月の欠測数を記録する。

## 4. リプレイと購読

### 4.1 役割分担

- `setup` は、エンティティの作成と購読の登録を担当する。
- `replay` は、観測値の書き込みだけを担当する。
- ブローカーの違い(URL、テナント、`@context` の渡し方)は、環境変数と引数で吸収する。

### 4.2 `setup`

1. 再生用テナントの既存の購読とエンティティを削除し、再生の開始直前の観測値で、10区のエンティティを作り直す。
2. 購読は次の3本を登録する。通知は MQTT で、QoS 0 とする。

| 購読 | トピック | 条件 |
|---|---|---|
| 全観測値 | `amedas/live` | なし |
| 降雪量 5cm/h 以上 | `amedas/cond/snowfall1h_ge5` | `q=snowfall1h>=5`、`watchedAttributes=["snowfall1h"]` |
| 降雪量 3cm/h 以上 | `amedas/cond/snowfall1h_ge3` | `q=snowfall1h>=3`、`watchedAttributes=["snowfall1h"]` |

条件付き購読は、条件が成立している間、書き込みのたびに通知が届く(遷移の瞬間だけの通知は、標準の `q` ではできない)。そこで `snowfall1h` は**毎正時の行にだけ書き込み**、`watchedAttributes` で監視対象を絞る。これで「その時間に条件を満たした」通知になる(2025年11月17〜18日の5cm/h 以上は5件、3cm/h 以上は16件)。

### 4.3 `replay`

- 引数は `--from`、`--to`(観測の何番目か、または日時)、`--interval`(1ステップ=観測10分に当てる実時間のミリ秒)、`--tenant`、`--broker-url`。
- 1ステップごとに、10区のエンティティへ属性を PATCH する。区の間も逐次に書き込む(1.5)。
- ステップの時刻は `t0 + i × interval` で決め、遅れを累積させない。ステップごとに実際の遅れを測り、一定以上なら警告を出す。
- 各 PATCH に `sentAt`(`{"@type":"DateTime","@value":"…Z"}` 形式の Property、ミリ秒精度)を付ける。地図アプリは、受信時刻との差から配信の遅延を算出する(ブローカーと地図アプリが同一ホストであることが前提)。
- 非 2xx の応答は数えて表示し、連続して失敗した場合は中断する。
- 再生は一方向に1回通す。ループ再生は作らない。やり直すときは `setup` を再実行する。

### 4.4 公開リポジトリでの既定値

- `compose/` は Stellio と Mosquitto。Mosquitto の WebSocket のポートは `127.0.0.1` にだけ公開する。
- Stellio は、デモと同じ速度(0.8秒/ステップ)では通知が最大で約13分遅れる。README の既定の `--interval` は、遅れが出ない速度まで落とす。実際の値は、実装時に実測して決める。
- 公開側のスクリプトは、どのブローカーでも同じ引数で動く。GeonicDB で動かす手順は非公開側に置く。

### 4.5 扱わない範囲

- Temporal API(再生にもライブ側にも不要)。
- 複数ブローカーのアダプター層。
- GeonicDB 内蔵の WebSocket。
- `throttling`(壁時計の秒で間引くため、加速した時計の遷移とは対応しない)。

### 4.6 検証

- ステップの時刻計算と、PATCH ボディの組み立ては純関数にして、`node:test` で単体テストする。
- 結合テストは、compose 上の Stellio へのスモークテストとする。再生した件数と、MQTT で受信した件数が一致することを確認する。

## 5. 地図アプリ(`web/`)

試作で検証した6演出を本実装する。Vite(素の JavaScript)で、地図のタイルは使わない(MapLibre の background と GeoJSON で描画し、外部通信なしで動作する)。

### 5.1 モジュール構成

| モジュール | 役割 | 依存 |
|---|---|---|
| `mqtt-feed` | MQTT の WebSocket に接続し、通知を購読する。通知を `Observation`(区、属性、`observedAt`、`sentAt`、購読の種別)に正規化する | mqtt.js |
| `dedupe` | 同じ書き込みの通知が、`ge3` と `ge5` の購読で別々に届く場合に、強い方の1件に集約する | なし(純関数) |
| `store` | 区ごとの最新値と、統計(通知レート、遅延の中央値・p95・最大、条件ヒット数)を保持する | なし(純関数) |
| `map-layer` | 区の面を積雪深の連続色で塗る。円表示への切替も提供する | MapLibre |
| `effects/` | 波紋(CSS)、雪の粒(canvas)、条件ヒットのラベル、音 | なし |
| `panels/` | HUD、2つの時計、条件ヒット欄、通知ログ、切替ボタン | なし |
| `live-widget` | 当日の最新の気象値(気象庁アメダス「札幌」) | fetch |

### 5.2 採用する演出

1. HUD(通知レート、配信の遅延)。遅延は `受信時刻 − sentAt`。
2. 2つの時計。見出しは「観測時刻」と「現在時刻」。
3. 波紋。通常は控えめにし、条件付き購読の通知は橙(3cm以上)・赤(5cm以上)の太い波紋とラベルにする。
4. 条件ヒット欄と通知ログ。ヒット欄を主役にする。
5. ダーク背景、区の面表示、降雪量に連動した雪の粒。
6. 音は任意で、発表者が切り替えられる。冒頭に「音を有効化」ボタンを1回押す必要がある。

### 5.3 試作からの修正点

- 白い文字が、積雪の多い区の面の上で読みにくくなる問題を直す(ラベルに縁取りか背景を付け、面の色の上限を調整する)。
- 時計の見出しを「再生時刻」から「観測時刻」に変更する。
- 雪の粒の描画解像度を `min(devicePixelRatio, 1.5)` に抑える(Retina での負荷対策)。
- ヒットの重複排除は、窓の長さではなく、**書き込みの識別子(区と観測時刻)で集約**する。強い購読の通知が来たら、弱い方の演出を置き換える。
- 区の境界は、国土数値情報の元データから作り直したものを使う。出典を画面左下に常時表示する。
- 札幌市であることを、画面のタイトルに明示する。

### 5.4 当日の最新値(`live-widget`)

- 気象庁アメダス「札幌」(観測所 14163)の最新値を、画面の隅の小さな表示として出す。会場のネットワークがある場合だけ表示し、取得に失敗したら非表示にする。主画面の動作には影響させない。
- 積雪の値は、冬季の観測が再開してから形式を確認する。それまでは気温と風を対象にする。

### 5.5 設定

- ブローカーの MQTT WebSocket の URL は、URL パラメーターで渡す(既定は `ws://127.0.0.1:9001`)。
- 表示範囲は観測点の範囲に合わせる。南区は途中で切れてもよい。

### 5.6 検証

- 純関数(`dedupe`、`store`、雪の粒の強度、面の色の変換)は、`node:test` で単体テストする。
- 画面は Playwright で確認する(通常の更新、条件ヒットの連写、ピーク時の画面)。
- 取りこぼしの確認は、リプレイの送信ログと、ブラウザの受信数を突き合わせる(`?debug` で受信ログを出す)。
- 実機の Retina、外部ディスプレイ、長時間の動作、音の聞こえ方は、実装後に確認する。
