# 札幌積雪タイムラプス: NGSI-LD ブローカーによるリアルタイム配信デモ 設計書

- 作成日: 2026-10-04
- 関連: [Issue #2](https://github.com/geolonia/geonicdb-amedas-demo/issues/2)、親 [Issue #1](https://github.com/geolonia/geonicdb-amedas-demo/issues/1)
- 状態: ドラフト(1回目のレビューを反映済み。ユーザーの確認待ち)

## 1. 目的と前提

### 1.1 目的

FOSS4G Hokkaido 2026(2026-11-28、トナリエ北広島、持ち時間 15〜20分(質疑を含む))での発表で使うデモを作る。NGSI-LD ブローカーのリアルタイム配信で何ができるかを、札幌市10区の2025年11月の観測データを使った積雪タイムラプスで見せる。

### 1.2 成功の基準

1. 会場のノート PC 1台で、取りこぼしなく動作する(ブローカー、Mosquitto、リプレイ、地図がすべてローカル)。
2. 第三者が、OSS のブローカー(Stellio)で再現できる形で GitHub に公開されている。
3. 「録画の再生ではなく、いま配信されている」ことが、画面から伝わる。

### 1.3 決定済みの前提

| 項目 | 内容 |
|---|---|
| 主題 | ブローカーという一般的な仕組み(OSS でも実現できる)で、どのようなリアルタイム配信ができるかを示す。「天気アプリの代わり」ではなく「ブローカーによるリアルタイム配信のショーケース」と位置づける |
| データ | 札幌市10区の観測データ(2025年11月、10分値、CC BY 4.0)。北広島市には公開された観測データがないため、対象は札幌市に統一し、画面と発表で札幌市と明示する |
| 配信経路 | リプレイ用プログラムが観測値をブローカーへ順次書き込む。ブローカーの購読通知(NGSI-LD Subscription、MQTT)が、Mosquitto の WebSocket を通って地図アプリに届く |
| 本番のブローカー | 発表の当日は、ローカルで動かす GeonicDB を使う(2026-10-03 の決定)。ローカルの GeonicDB は通知の遅延が小さく(約50ms)、加速した再生に耐えることを試作で確認済み。Issue #2 の初期案(ブラウザが Temporal API を取得して再生し、購読はライブ側だけに使う)から、「ブローカーが書き込みごとに通知を送る」形に変更した理由は、これが発表の主題そのものであるため |
| 公開 | コードは GitHub で公開する。公開リポジトリの手順は、OSS のブローカー(Stellio + Mosquitto の docker-compose)で動く形にする。Stellio では、通知の遅れを避けるため再生速度を落とす(4.4)。製品固有の起動手順は非公開側に置く |
| 対象外 | 除雪出動のシミュレーション、ひまわり衛星画像。定点カメラは当日の補助的な見せ方にとどめ、この設計書の範囲外とする |

### 1.4 リポジトリの扱い

`geolonia/geonicdb-amedas-demo` は、すでに PUBLIC である。このリポジトリを使い続け、README と説明文を札幌積雪デモ向けに書き換える(2026-10-04 に確定)。リポジトリ名に GeonicDB が残るが、発表では「このデモを動かしているブローカーの一つ」として扱う。

### 1.5 不変条件

- ブローカーへの書き込みは、**区の間も含めて逐次**に行い、並列にしない(ブローカーによっては、並列の書き込みで通知を取りこぼすため)。
- 再生した値が、ライブの値や過去の履歴と混ざらないようにする。同じエンティティへの再書き込みは、どのブローカーでも時系列履歴を汚す。ライブ用のデータと共存させる場合は、再生用のテナントを分ける。公開側の compose は再生専用のため、既定のテナントで足りる(4.4)。
- 公開リポジトリ(設計書を含む)には、特定のブローカー製品の内部情報、ソース、SDK、調査レポート、`.env`、認証情報を含めない。製品固有の根拠は、非公開側の資料に置く。
- 区の境界データは、国土数値情報の元データから作り直す(試作で使った配布元はライセンス表記がない)。

## 2. 全体構成

### 2.1 データの流れ

```
札幌市 CKAN (CSV)
   │ ① prepare(ビルド時に1回)
   ▼
data/*.json  (観測値 + 観測地点)
   │ ② setup: エンティティ作成と購読登録
   ▼
NGSI-LD ブローカー ◄── ③ replay(時計に合わせて逐次 PATCH)
   │ 通知(MQTT)
   ▼
Mosquitto ── WebSocket ──► ④ web(MapLibre + mqtt.js)
```

### 2.2 方式

Node.js の小さなスクリプト群と、Vite 製(素の JavaScript)の静的な地図アプリを、1つのリポジトリに置く。ブローカーは標準の NGSI-LD API だけで操作し、ブローカー間の違いは環境変数と引数で吸収する。アダプター層、型付きの SDK は作らない(発表までの期間に対して過剰であり、OSS での再現性にも寄与しないため)。

### 2.3 リポジトリ構成

| パス | 役割 |
|---|---|
| `scripts/prepare/` | CSV → NGSI-LD 向け JSON への変換。出典と加工内容を明記する |
| `scripts/replayer/` | `setup`(エンティティ作成と購読登録)と `replay`(逐次書き込み) |
| `web/` | 地図アプリ |
| `compose/` | Stellio と Mosquitto の docker-compose(主経路) |
| `data/` | 変換後の観測値、観測地点、区の境界、出典(`ATTRIBUTION.md`) |
| `docs/` | 設計書、実装計画 |

## 3. データ変換と観測地点

### 3.1 入力

札幌市 CKAN のデータセット `sapporo_weather` から、2025年の10区分の CSV を取得する(CC BY 4.0)。対象は **2025-11-01〜11-30 のみ**。CSV は UTF-8(BOM 付き)で、列は `日付, 時刻, 気温(℃), 風向(度), 風速(m/s), 降水量(mm), 積雪深(cm), 前１時間降雪量(cm)`。

### 3.2 変換(`scripts/prepare/`)

- 取得した CSV は `data/raw/` にキャッシュする(gitignore)。
- 変換は純関数にする。CSV の文字列を入力に受けて、観測値の配列を返す。
- 取り扱いのルール:
  - BOM を除去する。
  - 時刻は `H:MM` 形式(`0:10` のようにゼロ埋めがない)。`24:00` は、翌日の `00:00` として扱う。
  - 時刻は JST で解釈し、`observedAt` は UTC の ISO 8601 で出力する(例: 11/30 の `24:00` は 11/30T15:00Z)。
  - **欠測は全角の `×`**(CKAN のデータセット説明に記載)。積雪深には `-` の欠測が1行ある(豊平区)。欠測は、その属性を省略する(0 や NaN にしない)。属性ごとに独立して扱う。実データの欠測数は、気温が各区で823〜1,402行、風向・風速が1〜170行(厚別区が最大)、降水量が最大10行。気温の欠測は11/1〜10付近に限らない。
  - 前1時間降雪量の `-` は、正時以外の行に値がないという意味で、欠測ではない。正時の行にだけ値を持たせる(保持して書き込み続ける形にはしない)。正時の行の `×` は欠測として扱う。

### 3.3 出力(コミットする)

| ファイル | 内容 |
|---|---|
| `data/observations/<ward>.json` | 区ごとの観測値 |
| `data/stations.json` | 観測地点のメタ情報(区コード、名称、座標、出典、備考) |
| `data/wards.geojson` | 区の境界(3.5) |
| `data/ATTRIBUTION.md` | 札幌市(CC BY 4.0)、国土数値情報(国土交通省)、気象庁の出典と、加工内容 |

変換後のデータ(約2MB)をコミットする目的は、再現時の手間を減らすことにある。

### 3.4 NGSI-LD のモデル

- エンティティの型は `WeatherObserved`、ID は `urn:ngsi-ld:WeatherObserved:sapporo-<ward>`。
- 属性は `temperature`、`snowHeight`、`precipitation`、`windSpeed`、`windDirection`(CSV の風向。度)、`snowfall1h`。それぞれに `unitCode` と `observedAt` を付ける。加えて、配信の遅延の計測用に `sentAt`(4.3)を、書き込みごとに付ける。
- 位置は、観測点(土木センター)の座標を `GeoProperty` として持たせる。
- 区の面の描画は地図側の責務とし、NGSI-LD 側には持たせない。
- ID の `<ward>` は、次の表の綴りに固定する(CKAN のファイル名は綴りが揺れているため、そこから取らない)。

| 区 | `<ward>` | 区 | `<ward>` |
|---|---|---|---|
| 中央区 | `chuo` | 豊平区 | `toyohira` |
| 北区 | `kita` | 清田区 | `kiyota` |
| 東区 | `higashi` | 南区 | `minami` |
| 白石区 | `shiroishi` | 西区 | `nishi` |
| 厚別区 | `atsubetsu` | 手稲区 | `teine` |

### 3.5 観測地点の座標と区の境界

- 観測地点の座標は、各区の土木センターの所在地から作る(国土地理院の住所検索などを使う)。
- **北区は観測点が2か所ある**(発表者の事前調査による。CKAN の説明は「土木センター10か所」としており、公開資料での裏付けは未確認)。データがどちらのものかを、実装の最初に確認する。確定できなければ、確認結果と判断をこの設計書に追記する。座標は、確定するまで暫定値として扱う。
- 住所検索に国土地理院のサービスを使う場合は、その利用規約に従って出典を扱う(規約は実装時に確認する)。
- 区の境界は、国土数値情報の行政区域(N03)の元データから、札幌市10区を抽出して作る。出典を画面とドキュメントに表記する。

### 3.6 検証

- `node:test` で、BOM、`24:00`、欠測、JST→UTC、正時の判定を単体テストする。
- 件数チェック: 1区あたり 30日×144点=4,320行であること、属性別の欠測数が上記の範囲に収まることを確認する。
- 変換スクリプトは、元 CSV の取得日と、CKAN のデータセットの更新日(2026-06-29 時点)を、`data/ATTRIBUTION.md` か `data/` 内のメタ情報に記録する。

## 4. リプレイと購読

### 4.1 役割分担

- `setup` は、エンティティの作成と購読の登録を担当する。
- `replay` は、観測値の書き込みだけを担当する。
- ブローカーの違い(URL、テナント、`@context` の渡し方)は、環境変数と引数で吸収する。

### 4.2 `setup`

1. このデモが作った ID(`urn:ngsi-ld:WeatherObserved:sapporo-<ward>`)のエンティティと、このデモが登録した購読(トピックが `amedas/` で始まるもの)だけを削除し、再生の開始直前の観測値で、10区のエンティティを作り直す。それ以外のデータには触れない。
2. 購読は次の3本を登録する。通知は MQTT で、QoS 0 とする。

| 購読 | トピック | 条件 |
|---|---|---|
| 全観測値 | `amedas/live` | なし |
| 降雪量 5cm/h 以上 | `amedas/cond/snowfall1h_ge5` | `q=snowfall1h>=5`、`watchedAttributes=["snowfall1h"]` |
| 降雪量 3cm/h 以上 | `amedas/cond/snowfall1h_ge3` | `q=snowfall1h>=3`、`watchedAttributes=["snowfall1h"]` |

条件付き購読は、条件が成立している間、書き込みのたびに通知が届く(遷移の瞬間だけの通知は、標準の `q` ではできない)。そこで `snowfall1h` は**毎正時の行にだけ書き込み**、`watchedAttributes` で監視対象を絞る。これで「その時間に条件を満たした」通知になる。件数は再生の範囲による。既定の範囲(4.3)では、5cm/h 以上が5件、3cm/h 以上が16件(試作の再生範囲での実測)。2025年11月全体では、5cm/h 以上が12件、3cm/h 以上が39件ある。

### 4.3 `replay`

- 引数は `--from`、`--to`(日時。ISO 8601)、`--interval`(1ステップ=観測10分に当てる実時間のミリ秒)、`--tenant`、`--broker-url`。
- 既定の範囲は、`--from 2025-11-18T02:50+09:00` から `--to 2025-11-19T00:00+09:00`(128ステップ。北区の積雪深が35cmに達する日を含む)。`--interval 1000` なら約2分8秒。発表のデモの尺は、持ち時間の確定後に決める(8章)。11月全体(4,320ステップ)は、`--interval 800` でも約57分かかるため、既定にはしない。
- **通知を受けた地図アプリが「再生の終端」を判別する必要はない**。`replay` は、終了時にログへ件数を出すだけでよい。
- 1ステップごとに、10区のエンティティへ属性を PATCH する。区の間も逐次に書き込む(1.5)。
- ステップの時刻は `t0 + i × interval` で決め、遅れを累積させない。ステップごとに実際の遅れを測り、一定以上なら警告を出す。
- 各 PATCH に `sentAt`(`{"@type":"DateTime","@value":"…Z"}` 形式の Property、ミリ秒精度)を付ける。地図アプリは、受信時刻との差から配信の遅延を算出する(ブローカーと地図アプリが同一ホストであることが前提)。
- 非 2xx の応答は数えて表示し、**連続して5回失敗したら中断する**。ステップの遅れが `--interval` の2倍(下限1秒)を超えたら警告を出す。
- `sentAt` は毎回書く。ブローカーによっては、属性の書き込みごとに購読を評価するため、`sentAt` も負荷になる。負荷が問題になるなら、`sentAt` を毎ステップではなく正時の書き込みにだけ付ける(遅延の計測は、正時の通知だけで足りる)。
- 再生は一方向に1回通す。ループ再生は作らない。やり直すときは `setup` を再実行する。

### 4.4 公開リポジトリでの既定値

- `compose/` は Stellio、Mosquitto、**`@context` を配信する静的サーバー**の3つ。試作では、Stellio が `@context` を URL でしか受け付けなかったため、静的サーバー(`weather.jsonld`)が必要だった。Stellio が ETSI のコア context をネットワークから取得するかは未確認。会場でネットワークを切っても動くように、context は compose の内側から配信する。
- Mosquitto は、WebSocket のリスナーを持ち、`allow_anonymous true` とする。ポートは `127.0.0.1` にだけ公開し、その旨を README に明記する。
- テナントは、既定のテナント(ヘッダーなし)を使う。Stellio のテナントは、環境変数での事前の宣言と再起動が必要なため、公開側では使わない。
- 購読の MQTT の宛先と `notifierInfo`(MQTT のバージョン、QoS)は、`setup` の設定項目(環境変数)として外に出す。Stellio は compose 内の `mqtt://mosquitto:1883/<topic>` と `mqtt5.0`、他のブローカーは別の値になる。
- 通知の形式は、ブローカーによって異なる。ETSI の MQTT バインディングは `{"body":…, "metadata":…}` の封筒形式で、これを使わないブローカーもある。地図アプリ(`mqtt-feed`)は、`msg.body ?? msg` で両方を受ける。
- **Stellio は、デモと同じ速度(0.8秒/ステップ)では、通知が最大で約13分遅れる**(試作の実測)。10区×約6属性が、属性ごとに別のイベントとして購読を評価されるため。README の既定の `--interval` は、遅れが出ない速度まで落とす。限界の速度は未測定で、**工程2の最初に測る**。届かなければ、変化した属性だけを PATCH する、区の間隔を空ける、などで負荷を減らす。
- 公開側のスクリプトは、どのブローカーでも同じ引数で動く。製品固有の起動手順は非公開側に置く。

### 4.5 扱わない範囲

- Temporal API(再生にもライブ側にも不要)。
- 複数ブローカーのアダプター層。
- ブローカー固有の WebSocket 配信(標準の MQTT 通知だけを使う)。
- `throttling`(壁時計の秒で間引くため、加速した時計の遷移とは対応しない)。

### 4.6 検証

- ステップの時刻計算と、PATCH ボディの組み立ては純関数にして、`node:test` で単体テストする。
- 結合テストは、compose 上の Stellio へのスモークテストとする。再生した件数と、MQTT で受信した件数が一致することを確認する。

## 5. 地図アプリ(`web/`)

試作で検証した6演出を本実装する。Vite(素の JavaScript)で、地図のタイルは使わない(MapLibre の background と GeoJSON で描画し、外部通信なしで動作する)。

### 5.1 モジュール構成

| モジュール | 役割 | 依存 |
|---|---|---|
| `mqtt-feed` | MQTT の WebSocket に接続し、通知を購読する。通知を `Observation`(区、属性、`observedAt`、`sentAt`、購読の種別)に正規化する | mqtt.js |
| `dedupe` | 同じ書き込みの通知が、`ge3` と `ge5` の購読で別々に届く場合に、強い方の1件に集約する | なし(純関数) |
| `store` | 区ごとの最新値と、統計(通知レート、遅延の中央値・p95・最大、条件ヒット数)を保持する | なし(純関数) |
| `map-layer` | 区の面を積雪深の連続色で塗る。円表示への切替も提供する | MapLibre |
| `effects/` | 波紋(CSS)、雪の粒(canvas)、条件ヒットのラベル、音 | なし |
| `panels/` | HUD、2つの時計、条件ヒット欄、通知ログ、切替ボタン | なし |
| `live-widget` | 当日の最新の気象値(気象庁アメダス「札幌」) | fetch |

### 5.2 採用する演出

1. HUD(通知レート、配信の遅延)。遅延は `受信時刻 − sentAt`。
2. 2つの時計。見出しは「観測時刻」と「現在時刻」。
3. 波紋。通常は控えめにし、条件付き購読の通知は橙(3cm以上)・赤(5cm以上)の太い波紋とラベルにする。
4. 条件ヒット欄と通知ログ。ヒット欄を主役にする。
5. ダーク背景、区の面表示、降雪量に連動した雪の粒。
6. 音は任意で、発表者が切り替えられる。冒頭に「音を有効化」ボタンを1回押す必要がある。

### 5.3 試作からの修正点

- 白い文字が、積雪の多い区の面の上で読みにくくなる問題を直す(ラベルに縁取りか背景を付け、面の色の上限を調整する)。
- 時計の見出しを「再生時刻」から「観測時刻」に変更する。
- 雪の粒の描画解像度を `min(devicePixelRatio, 1.5)` に抑える(Retina での負荷対策)。
- ヒットの重複排除は、窓の長さではなく、**書き込みの識別子(区と観測時刻)で集約**する。`ge3` と `ge5` は別の購読のため、同じ書き込みの通知が別々に、順不同で届く(試作では40ms以上ずれて二重表示になった)。強い購読の通知が後から届いたら、弱い方の演出を置き換える。弱い購読の通知が後から届いたときは、すでに強い方の演出が出ていれば無視する。通知の遅延が大きいブローカーでも、演出は届いた順に出す(観測時刻に合わせて遅らせない)。
- 区の境界は、国土数値情報の元データから作り直したものを使う。出典を画面左下に常時表示する。
- 面の色の刻みは、試作と同じ 0、5、15、25、35cm とする(暗い青から白への連続色)。
- 札幌市であることを、画面のタイトルに明示する。

### 5.4 当日の最新値(`live-widget`)

- 気象庁アメダス「札幌」(観測所 14163)の最新値を、画面の隅の小さな表示として出す。会場のネットワークがある場合だけ表示し、取得に失敗したら非表示にする。主画面の動作には影響させない。
- 積雪の値は、冬季の観測が再開してから形式を確認する。それまでは気温と風を対象にする。
- 取得元は、気象庁の bosai の JSON(`https://www.jma.go.jp/bosai/amedas/data/point/14163/<日時>.json`)。CORS は許可されている(確認済み)。ただし、公式の API 仕様ではないため、形式が変わる可能性がある。
- 出典(気象庁)と、加工した旨を、ウィジェットの近くに表示する。取得に失敗したときは、出典の表示も出さない。

### 5.5 設定

- ブローカーの MQTT WebSocket の URL は、URL パラメーターで渡す(既定は `ws://127.0.0.1:9001`)。
- 表示範囲は観測点の範囲に合わせる。南区は途中で切れてもよい。

### 5.6 検証

- 純関数(`dedupe`、`store`、雪の粒の強度、面の色の変換)は、`node:test` で単体テストする。
- 画面は Playwright で確認する(通常の更新、条件ヒットの連写、ピーク時の画面)。
- 取りこぼしの確認は、リプレイの送信ログと、ブラウザの受信数を突き合わせる(`?debug` で受信ログを出す)。
- 実機の Retina、外部ディスプレイ、長時間の動作、音の聞こえ方は、実装後に確認する。

### 6.2 公開前のチェック

- 試作のコード、試作の `data/`、スクリーンショット、起動用のスクリプトをコピーしない。必要な部分は書き直す。
- **最初のコミットより前に**、`.gitignore`(`.env`、`data/raw/`、`.playwright-mcp/`、`node_modules/`)とシークレットのスキャンの設定を入れる(工程0)。現状、リポジトリには `.gitignore` がない。
- シークレットのスキャンを CI に入れる(Geolonia の標準に従う)。
- リポジトリの説明文と README を、札幌積雪デモ向けに書き換える。

### 7.1 地図アプリの優先度

発表(2026-11-28)まで約8週間で、レビューを各工程に挟む。地図アプリは、次の優先度で作り、時間が足りなければ下から削る。

| 優先 | 内容 |
|---|---|
| 必須 | 面表示、2つの時計、HUD(配信の遅延)、通常の波紋、条件ヒット(強い波紋、ラベル、ヒット欄) |
| 次点 | 通知ログ、ダーク背景の仕上げ、当日の最新値(応募概要の「当日の最新値との比較」に対応するため、削る前に Issue #2 の記載と合わせる) |
| 余裕があれば | 雪の粒(負荷が最も重く、「いま配信されている」ことの証拠にはならない)、円表示の切替、音 |
